## The proposal under review

Claim set:
1. beanxsound no longer depends on FxSound in code (fxsound.rs deleted, no process spawns, engine
   owns state/presets, DSP in `beanxdsp`), but it processes no audio at all, so the app is a UI.
2. The APO path is the right route for system-wide DSP; a virtual device is the fallback.
3. On this build a bare HKCR registration does not get instantiated, and the difference between
   our registration and the APOs that do work is (a) packaging as a signed APO-class driver
   package, and (b) the `{c792e395-...},100` software-component reference on the endpoint.
4. Installing our APO as an APO-class package with a self-signed, locally trusted catalog is
   acceptable for a personal machine, and avoids buying a certificate.
5. Next steps proposed: (i) control experiment with a known-good third-party APO (Equalizer APO)
   to decide whether the classic path is closed; (ii) link a component node to the endpoint;
   (iii) wire `beanxdsp` and the shared-memory bus into the APO; (iv) `beanxctl` with journal +
   restore; (v) meter path from the stream; (vi) one preset store and README cleanup; (vii)
   uninstall FxSound and remove the FxSound Speakers endpoint.

## Known gaps in the proposal

- No control experiment yet: nothing proves an unsigned, classically registered APO cannot load
  on build 26300. Every APO that works here is Microsoft-signed and packaged.
- The marker never appearing is only meaningful now that the log directory is writable by
  LOCAL SERVICE; earlier attempts could have failed silently for that reason.
- `audiodg` module list could not be read unelevated ("Access is denied"), so it is unproven
  whether audiodg ever mapped `beanxapo.dll`.
- The Razer endpoint's THX APO chain entry was overwritten with our CLSID and is not restored.
