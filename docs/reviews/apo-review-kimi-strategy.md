# Verdict

**Choose a componentized APO: an extension INF attached to an existing audio-device parent, plus an `AudioProcessingObject` component INF. Use the existing locally trusted self-signed certificate for both catalogs and leave the DLL unsigned. Do not choose a virtual audio driver.**

“Unsigned DLL, no paid certificate” is achievable on this personally controlled machine; **“no signing at all” is not** for the component route because PnP needs trusted catalogs. The earlier `pnputil` success already demonstrates catalog trust. It did not test an APO installation: without an extension INF's `AddComponent`, no parent enumerated the SWC child, so the component INF had nothing to bind to and correctly copied nothing.

For this to work, all of the following must hold:

- The APO must be a PnP child of the actual audio device, with the endpoint's `,100` component reference generated by that association. **False now:** no beanx SWD node exists.
- The component INF must use driver-package-isolated `HKR` registration and a DriverStore DLL path, not merely global HKCR keys. **False now.**
- `audiodg` must actually be unprotected for an unsigned DLL, or the DLL must have the trust Windows demands for protected playback. `DisableProtectedAudioDG=1` is set, but post-restart protection was not queried, so this is **unproven**, not established.
- The COM object must satisfy the APO contract. **False now:** `PassThroughApo` implements three interfaces but omits Microsoft's required `IAudioSystemEffects`. `CoCreateInstance=S_OK` therefore proves only class-factory plumbing. The release profile's panic behavior and missing entry-point containment also remain unacceptable.
- The graph must call `Initialize`/`LockForProcess`, then `APOProcess`, and the APO must link `beanxdsp`. **All false now.** The app currently edits state and endpoint peak meters; it processes no samples.

The classic unsigned-HKCR route is not proven impossible, but it is the wrong product architecture. Microsoft's component model explicitly scopes APOs to parent drivers; the plan's “register one global CLSID on every endpoint and repair it with a watcher” conflicts with that model. Retain the DSP/state separation, but replace Wave 0 with the component test below, then wire shared memory and DSP only after lifecycle and frame proof.

# The one experiment

Run **one complete two-package component installation against the existing `ROOT\FXVAD` parent**, not another Razer registry write. This isolates the physical devices and tests the exact missing mechanism. The test DLL must first add `IAudioSystemEffects`, use unwind/panic containment, and retain the lifecycle/frame evidence. Give both INFs a newer `DriverVer`; omit `SignatureAttributes.PETrust`, which is an HLK signing request, not something a self-signed certificate can manufacture.

From an elevated SDK Developer PowerShell, after authoring `beanxext.inf` (`Class=Extension`, owned `ExtensionId`, model `ROOT\FXVAD`, `AddComponent=BeanxApo`) and `beanxapo.inf` (`Class=AudioProcessingObject`, model `APO\VEN_BEANX&CID_BEANXAPO`, DriverStore `CopyFiles`, `HKR` registrations):

```powershell
Set-Location 'Z:\luxdev-z\Dev\002-Tier-Two-Projects\beanxsound\crates\beanxapo\install'
pnputil /delete-driver oem44.inf /uninstall /force   # previous package is unbound
reg delete 'HKCR\CLSID\{6F2F0B1C-3C1E-4A5F-9C1D-2B7A5C0E9D41}' /f
reg delete 'HKCR\AudioEngine\AudioProcessingObjects\{6F2F0B1C-3C1E-4A5F-9C1D-2B7A5C0E9D41}' /f
makecat .\beanxext.cdf
makecat .\beanxapo.cdf
signtool sign /sm /n 'LuxDev beanxsound Test' /fd SHA256 .\beanxext.cat .\beanxapo.cat
pnputil /add-driver .\beanxapo.inf
pnputil /add-driver .\beanxext.inf /install
Get-PnpDevice -Class AudioProcessingObject | Where-Object FriendlyName -Match 'beanx'
reg query 'HKLM\SYSTEM\CurrentControlSet\Enum\SWD\DRIVERENUM' /s /f BEANX
Restart-Service AudioEndpointBuilder -Force
Restart-Service Audiosrv -Force
```

Select **FxSound Speakers** as default in the existing app and play ten seconds of audio, then:

```powershell
Get-Content 'C:\ProgramData\beanxsound\apo-load.log' -Tail 20
```

Branches:

- **No SWD child:** extension targeting/installation is wrong. Do not touch DLL signing or write more endpoint values.
- **Child exists but no `Initialize`:** parent association worked; the remaining failure is COM registration or load trust, not `AddComponent`. A Microsoft-signed build of the identical package then distinguishes trust from implementation.
- **`Initialize`/`LockForProcess` appear but frames stay zero:** the DLL loads; diagnose graph construction, slot selection and actual endpoint routing.
- **Frames increase and a subsequent −12 dB setting measures −12 dB by loopback:** the chosen route is validated with no paid certificate. Productize per-parent component packages; only then expand DSP/UI work.

# What not to do

- **Do not rerun the same HKCR test or overwrite THX again.** It cannot distinguish a platform restriction from the currently incomplete COM object, and it damages a working OEM chain.
- **Do not copy THX's `PETrust` declaration into a self-signed package.** That requests Microsoft certification; it does not confer trust.
- **Do not disable Secure Boot, enable test-signing, disable driver-signature enforcement, patch/inject `audiodg`, or replace Microsoft/OEM DLLs.** Those enlarge machine-wide risk to avoid the correct user-mode packaging step.
- **Do not build a kernel virtual driver next.** It is slower, needs release signing, and has a larger failure domain than the viable component APO.
- **Do not treat `pnputil`, registry readback, green DSP tests, UI state, or `CoCreateInstance` as audio proof.** Require lifecycle calls, increasing frames, and a measured loopback delta.
- **Do not uninstall FxSound yet.** Its existing virtual parent is the isolated test fixture; remove it only after the real endpoints produce measured audio through beanxsound.
